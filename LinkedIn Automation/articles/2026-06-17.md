TITLE (paste into Medium title field):
Frontend System Design: Building a Real-Time Dashboard That Doesn't Melt the Browser

SUBTITLE (paste as first paragraph, then bold it in Medium):
From WebSocket frames to pixels: layers, batching, and the merge rules that actually matter.


Imagine a dashboard with 800 live rows, six KPI cards, and two charts. A new tick arrives every 50ms. On localhost, you wire socket.onmessage to setState and it feels fine. Ship it to staging on spotty 4G and the tab stutters. Scroll the grid and it gets worse. Open DevTools and React is reconciling the whole tree hundreds of times per second.

The WebSocket API is five lines. The frontend system around it is not.

This article breaks down how I'd design the client side of a real-time operational dashboard: not the Kafka cluster or the OLAP database, but the layers between the socket and the screen. The patterns here apply whether you're on React 19, Vue, or Svelte. The failure modes are the same.


The problem (and why demos lie)
[H2 in Medium]

A real-time dashboard has three jobs at once:

1. Ingest a stream of partial updates (not full snapshots every tick).
2. Merge those updates into stable, queryable state per widget.
3. Render only what changed, at a cadence humans can actually perceive.

Demos cheat. They update one number on a card. Production sends row patches, alert counts, chart points, and presence flags on the same connection. If every message triggers a React render, you don't have a dashboard. You have a stress test.

The hard part isn't opening a socket. It's decoupling transport from rendering so the UI stays responsive when the network doesn't.


Requirements
[H2 in Medium]

Functional
[H3 in Medium]

- Subscribe to multiple topics (e.g. summary metrics, incident feed, entity grid) with independent lifecycle.
- Apply partial updates: patch a row, append an event, replace a KPI value.
- Show last updated time and a clear degraded state during reconnect.
- Support user actions (acknowledge alert, change filter) without losing in-flight updates.
- Initial load from REST, then live stream takes over without a full-page refresh.

Non-functional
[H3 in Medium]

- Latency: perceived update within ~200ms (human perception floor; faster is wasted work).
- Throughput: handle 50–200 messages/sec per client without main-thread jank.
- Resilience: auto-reconnect with exponential backoff, resubscribe, and stale-data indicators.
- Memory: bounded buffers; don't accumulate unbounded event history in React state.
- Accessibility: live regions for critical alerts, not every tick.


High-level architecture
[H2 in Medium]

Don't let UI components talk to a raw socket. Put explicit layers between the network and the pixels.

1. Transport
[H3 in Medium]

WebSocket when you need bidirectional, low-latency channels: commands, presence, high-frequency entity grids.

Server-Sent Events (SSE) when the server only pushes one-way: status feeds, progress streams, notification counts. SSE rides HTTP, reconnects automatically, and plays nicer with some corporate proxies.

Pick per channel, not one winner for the whole app.

2. Connection manager (singleton)
[H3 in Medium]

One module owns:

- Open / close / reconnect with exponential backoff + jitter
- Auth token refresh before the socket dies silently
- Heartbeat / ping to detect half-open connections
- Subscription registry: which topics this tab wants, replayed after reconnect
- Routing raw frames to the event processor (never to React directly)

On reconnect, the UI must not pretend everything is fine. Show degraded mode, last good timestamp, and whether user actions are queued or disabled.

3. Event processor
[H3 in Medium]

Raw socket messages are untrusted input. This layer:

- Validates schema (even a lightweight check: required fields, known event types)
- Dedupes by event ID or sequence number
- Orders when the contract requires it (some feeds are eventually consistent; document which)
- Routes to the correct state boundary (grid store vs KPI store vs alert feed)
- Buffers high-frequency bursts before merge

4. State boundaries
[H3 in Medium]

Avoid one global useState for the entire dashboard. Isolation limits blast radius.

- Initial page / historical aggregates → TanStack Query (or similar). Caching, dedupe, background refetch.
- Live KPIs, grid rows, alert list → Per-widget store (Zustand, or external store). Scoped subscriptions, stable selectors.
- Ephemeral UI (panel open, sort column) → Local component state. Doesn't belong in the socket pipeline.

For high-frequency external data, keep the live store outside React. Components subscribe to snapshots via useSyncExternalStore. React doesn't own the firehose; it reads what it needs.

5. UI widgets
[H3 in Medium]

Each widget:

- Subscribes to a selector (e.g. "rows visible in viewport + sort key"), not the whole store
- Virtualizes lists with 50+ rows (TanStack Virtual, AG Grid, etc.)
- Memoizes chart inputs so a KPI tick doesn't repaint unrelated charts
- Throttles visual updates to requestAnimationFrame or ~100ms, whichever matches the widget


Critical data flow: socket to screen
[H2 in Medium]

>>> UPLOAD IMAGE: articles/assets/2026-06-17-dataflow.png <<<

The anti-pattern: onmessage → JSON.parse → setState. Every message schedules a render. At 100 msg/sec, React spends more time reconciling than the user spends reading.

The pattern that scales:

1. Append parsed events to a ref-based buffer (no render).
2. Flush on requestAnimationFrame or a fixed interval (e.g. 100ms).
3. Merge the batch into the external store with deterministic rules (see below).
4. Notify subscribers; React re-renders only components whose selector output changed.

For a virtualized grid, pass stable row object references when cell values didn't change. Recreating every row object every tick defeats memoization and makes AG Grid work harder for no reason.


Merge semantics (where bugs hide)
[H2 in Medium]

Document merge rules per event type before writing UI code.

- ROW_PATCH → Upsert by row ID; ignore if sequence ≤ stored sequence
- ROW_DELETE → Remove by ID; tombstone if undo matters
- KPI_UPDATE → Replace value + timestamp; animate only if delta exceeds threshold
- ALERT_NEW → Prepend to bounded ring buffer (max N items)
- FULL_SNAPSHOT → Replace entire slice (use sparingly; usually on reconnect)

Out-of-order delivery happens on reconnect and on multi-partition backends. If you don't track sequence numbers, you'll show stale data confidently. That's worse than showing a spinner.


Key tradeoffs
[H2 in Medium]

One socket vs many
[H3 in Medium]

One multiplexed WebSocket simplifies auth and reconnect. Multiple SSE channels simplify debugging and let you tune cache headers per feed. Hybrid is common: SSE for alerts, WebSocket for the interactive grid.

React state vs external store
[H3 in Medium]

React state is fine for low-frequency data (< 5 updates/sec per widget). Above that, external store + batching wins. React Compiler helps with memo boilerplate; it does not fix a firehose into setState.

Optimistic UI
[H3 in Medium]

Optimistic acks feel fast but need rollback paths when the command fails after reconnect. Queue commands while disconnected, replay on open, and surface conflicts ("someone else already acked this").

Polling fallback
[H3 in Medium]

When WebSockets are blocked, fall back to short polling with ETags or Last-Event-ID. Degraded, but usable. Hide the transport choice behind the connection manager so widgets don't care.


Failure modes I've debugged
[H2 in Medium]

1. Tab backgrounded: timers throttle; socket stays open but flush interval drifts. On visibilitychange, request a snapshot or catch-up delta.
2. Reconnect storm: 10k tabs reconnect at once after deploy. Backoff with jitter on the client; server-side rate limit on handshake.
3. Memory leak: forgotten onmessage handler after route change. Connection manager must be route-aware or truly app-global with explicit teardown.
4. Stale closure in socket callback: handler captures old dispatch. Bind handlers once; read latest subscription map from a ref.
5. Chart + grid shared context: one Context provider holds theme + live prices. Every tick re-renders the chart. Split contexts or move live data to external stores.


Performance notes
[H2 in Medium]

- Sample the stream, don't render the firehose. Users can't perceive sub-200ms updates on a KPI card. Match flush rate to widget type (grid vs sparkline vs alert badge).
- Virtualize early. 500 rows with DOM nodes is a pagination problem wearing a real-time costume.
- Web Workers for heavy client-side aggregation (rolling averages, anomaly scoring). Keep the main thread for input and paint.
- Measure with Production-like data. Chrome DevTools Performance tab with CPU 4x slowdown and "Offline" throttling catches what Profiler misses.


What I'd ship first (MVP order)
[H2 in Medium]

1. Connection manager with reconnect, backoff, and a visible "last updated" indicator.
2. REST initial load via TanStack Query for each widget's first paint.
3. One live widget (a single KPI or a small grid) with ref buffer + rAF flush + external store.
4. Merge rules in one module with unit tests for out-of-order and duplicate events.
5. Virtualized grid once row count justifies it, not before.
6. Second transport or polling fallback only after the happy path is stable in staging on bad networks.

Skip building all six widgets live on day one. Prove the pipeline on one surface, then clone the pattern.


Closing thought
[H2 in Medium]

Real-time frontend system design is less about which framework you pick and more about where you draw boundaries: socket vs processor vs store vs widget. Get those lines right and React Compiler, virtualization, and TypeScript are force multipliers. Blur them and no amount of useMemo saves you.

The senior habit: before adding a library, ask whether the bug is transport, merge, or render. Fix the right layer.
