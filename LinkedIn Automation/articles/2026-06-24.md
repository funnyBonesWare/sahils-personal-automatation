TITLE (paste into Medium title field):
Frontend System Design: Building a Typeahead That Doesn't Lie in Production

SUBTITLE (paste as first paragraph, then bold it in Medium):
From debounce to AbortController to WAI-ARIA: the layers between keystrokes and suggestions that demos skip.


Picture a global search bar at the top of a SaaS app. You type three characters. Suggestions appear. You backspace once. The list flickers to results from two keystrokes ago. You pick a suggestion with the keyboard. Focus jumps somewhere else. The screen reader announces nothing useful.

On localhost with a 20ms API, the demo feels perfect. Ship it to staging with 200ms latency and a user who types fast, and the UI starts lying. Not crashing. Just quietly showing stale data at the wrong moment.

The typeahead problem looks trivial. It is one of the best frontend system design exercises because every layer has a failure mode: input timing, network races, cache invalidation, keyboard focus, and accessibility contracts.

This article breaks down how I'd design a production autocomplete from the browser's perspective. Not the inverted index or the trie on the server (those matter too), but the client architecture that keeps suggestions fast, correct, and usable for everyone.


The problem (and why demos lie)
[H2 in Medium]

A typeahead has four jobs at once:

1. Turn noisy keystrokes into a controlled stream of search intents.
2. Fetch suggestions without hammering the API or racing yourself.
3. Render results with keyboard and screen-reader support.
4. Degrade gracefully when the network is slow, empty, or down.

Demos cheat. They debounce in a tutorial hook, mock instant responses, and skip keyboard navigation entirely. Production sends real requests over real networks while the user backspaces, pastes, and switches tabs mid-flight.

The hard part isn't calling `fetch` on input change. It's making sure the suggestion list always reflects the **current** query, never an older one that happened to arrive last.


Requirements
[H2 in Medium]

Functional
[H3 in Medium]

- Show suggestions after the user types a minimum prefix (e.g. 2 characters).
- Support keyboard navigation: arrow up/down, Enter to select, Escape to close.
- Support mouse click on a suggestion.
- Show recent or trending suggestions on focus (empty prefix).
- Highlight the matching substring in each suggestion.
- Clear suggestions when input is cleared or below minimum length.
- Optional: inline completion (ghost text after cursor) for power users.

Non-functional
[H3 in Medium]

- Latency: suggestions visible within ~300ms of the user pausing (p95).
- Correctness: displayed results must match the current input value, even with out-of-order responses.
- Load: at most one in-flight request per typing burst; cancel or ignore stale responses.
- Accessibility: WAI-ARIA combobox pattern; focus stays in the input; active option announced.
- Resilience: loading, empty, and error states that don't block typing.
- Memory: bounded client cache; no unbounded suggestion history in React state.


High-level architecture
[H2 in Medium]

Don't wire `onChange` directly to `fetch`. Split the client into explicit layers.

1. Input layer (combobox)
[H3 in Medium]

The visible `<input>` is not just a text field. It is a **combobox**: an input that controls a popup listbox. This layer owns:

- Raw input value (controlled component)
- Debounced query (derived, not the same as raw input)
- Popup open/closed state
- Active option index for keyboard highlight
- `aria-expanded`, `aria-controls`, `aria-activedescendant` on the input

Keep keyboard focus in the input at all times during navigation. Move the **active** highlight with `aria-activedescendant`, not by moving DOM focus into the list. Screen readers need this contract.

2. Request layer
[H3 in Medium]

One module (or hook) owns all network behavior:

- Debounce timer (200–300ms after last keystroke)
- `AbortController` to cancel the previous request when a new one starts
- Monotonic `requestId` ref: only apply a response if its ID matches the latest
- Minimum prefix length gate
- Loading / error flags scoped to the current query

Debouncing alone is not enough. Without abort + requestId, a slow response for `"re"` can overwrite fresh results for `"react"` after the user has moved on.

3. Cache layer
[H3 in Medium]

Small LRU cache keyed by normalized prefix (e.g. lowercase, trimmed):

- Instant results on backspace within a recent prefix
- Prefetch top suggestions on focus (empty prefix → trending/recent)
- TTL per entry (e.g. 60s for trending, 5min for stable catalog prefixes)

Cache hits skip the network but still run the requestId check against the current input value.

4. Presentation layer
[H3 in Medium]

Listbox popup, loading skeleton, empty state, error retry. Subscribes to suggestion state + active index. Does not own fetch logic.


Critical data flow: keystroke to suggestion list
[H2 in Medium]

>>> UPLOAD IMAGE: articles/assets/2026-06-24-race-condition.png <<<

The anti-pattern:

```
onChange → setQuery → useEffect → fetch → setSuggestions
```

Every keystroke schedules work. Slow responses win the race. Backspace shows wrong data. Unmount mid-request updates state on a dead component.

The pattern that scales:

1. **Raw input** updates immediately (input feels responsive).
2. **Debounced query** updates 250ms after pause (network intent).
3. On debounced change: increment `requestId`, abort prior controller, start new fetch with signal.
4. On response: if `requestId` !== latest, discard. If aborted, ignore. Else normalize and set suggestions.
5. On unmount / query below min length: abort, clear suggestions, reset active index.

TanStack Query helps here: `queryKey: ['suggest', debouncedQuery]` dedupes identical prefixes, and `enabled: debouncedQuery.length >= 2` gates short input. You still want explicit abort or stale-time tuning so a fast typist doesn't flash old cache entries from a different session shape.


Debounce vs throttle (pick debounce)
[H2 in Medium]

- **Debounce:** fire after the user stops typing. Best for typeahead. Cuts request volume by 80%+.
- **Throttle:** fire at most once per interval while typing continues. Better for scroll or resize, not search.

250ms is a good default. It sits near human reaction time so the UI still feels instant, but collapses a 10-character burst into 1–2 requests instead of 10.


Accessibility: non-negotiable for production
[H2 in Medium]

Follow the [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/):

| Role / attribute | Purpose |
| --- | --- |
| `role="combobox"` on input | Identifies the control type |
| `aria-expanded` | Popup open or closed |
| `aria-controls` | ID of the listbox popup |
| `aria-activedescendant` | ID of highlighted option while focus stays in input |
| `role="listbox"` on popup | Container for options |
| `role="option"` + `aria-selected` | Each suggestion row |

Keyboard contract:

- **Down / Up:** move active option, wrap at edges
- **Enter:** select active option, close popup, fire `onSelect`
- **Escape:** close popup, keep input value
- **Tab:** close popup, move focus naturally

Test with VoiceOver or NVDA, not just Chrome DevTools. A typeahead that only works with a mouse is not shippable in 2026.


Key tradeoffs
[H2 in Medium]

Client-side filter vs server suggest
[H3 in Medium]

Client filter works for small static lists (< 500 items). Server suggest scales to millions of records and supports ranking, typo tolerance, and personalization. Hybrid: server for prefix ≥ 2, client filter only for already-fetched recent items on focus.

Inline completion vs list-only
[H3 in Medium]

Inline ghost text (autocomplete="both") feels fast but confuses users when the completion string doesn't match intent. List-only (autocomplete="list") is safer for open-ended search. Pick per product surface.

Optimistic selection
[H3 in Medium]

On Enter, navigate immediately and fetch detail in the background. Feels snappy. Needs rollback if the selected ID 404s. For search bars that route to a results page, optimistic navigation is usually fine.

Global vs scoped typeahead
[H3 in Medium]

A global command palette (Cmd+K) shares one instance app-wide. Per-page filters (e.g. "search users in this project") need scoped API params and isolated cache keys. Don't reuse one hook with hidden global state unless you mean to.


Failure modes I've debugged
[H2 in Medium]

1. **Stale response wins:** fixed with AbortController + requestId, not debounce alone.
2. **Flash of empty on backspace:** cache previous prefix results; don't clear the list until the new fetch resolves or cache misses.
3. **Double fetch on Strict Mode remount:** guard with abort on cleanup; TanStack Query handles dedupe if queryKey is stable.
4. **Focus trap in popup:** never move focus to listbox options; use `aria-activedescendant`.
5. **Paste storm:** pasted 40 characters bypass debounce feel; run one immediate fetch on paste events, still with abort.
6. **Selected suggestion ≠ input value:** on select, set input to label, close popup, and cancel any in-flight suggest for the old prefix.


Performance notes
[H2 in Medium]

- Prefetch on focus: one cheap request for trending/recent saves perceived latency on first keystroke.
- Normalize query once (trim, lowercase, collapse spaces) before cache key and API param.
- Virtualize the suggestion list only above ~50 items; most typeaheads return 5–10.
- Don't store full suggestion objects in React context shared app-wide; keep state colocated with the combobox.
- Measure with Network throttling (Fast 3G) and CPU 4x slowdown. Localhost hides every race.


What I'd ship first (MVP order)
[H2 in Medium]

1. Controlled input + debounced query + minimum prefix length.
2. Fetch with AbortController and requestId guard (unit test the race scenario).
3. Loading, empty, and error UI that doesn't block typing.
4. Keyboard nav + WAI-ARIA combobox attributes (test with a screen reader).
5. LRU prefix cache + prefetch on focus.
6. Highlight matching substring and analytics on select vs free-text submit.

Skip personalization and typo tolerance on day one. Prove the pipeline is correct under fast typing and slow networks first.


Closing thought
[H2 in Medium]

Typeahead system design is a compact lesson in frontend boundaries: input timing, network correctness, cache, and accessibility are four different problems. Blur them into one `useEffect` and you get a demo. Separate them and you get something you'd trust in a global search bar.

The senior habit: when suggestions look wrong, ask whether the bug is debounce, stale response, cache, or render. Fix the right layer.
