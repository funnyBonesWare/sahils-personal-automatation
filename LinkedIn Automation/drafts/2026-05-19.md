The lesson wasn't "memoization is bad." It was that I'd been memoizing to feel senior — not because the profiler said to.

Most React performance advice stops at "wrap it in useMemo." But every memo has a cost the docs don't put in bold:

1️⃣ 𝗧𝗵𝗲 𝗵𝗶𝗱𝗱𝗲𝗻 𝗯𝗶𝗹𝗹 — useMemo runs your dependency comparison on every render, allocates a fresh closure, and stores both. For cheap computations (a { id, label } derivation, a sorted 20-item array), that bookkeeping costs more than just recomputing. You pay every render to skip work that wasn't expensive.

2️⃣ 𝗪𝗵𝗲𝗻 𝗶𝘁 𝗮𝗰𝘁𝘂𝗮𝗹𝗹𝘆 𝗽𝗮𝘆𝘀 — Two cases earn the overhead: (a) genuinely expensive compute on every render — parsing a large payload, building a derived index over thousands of rows, regex-ing through a config blob — and (b) preserving referential identity for a React.memo'd child that would otherwise re-render its whole subtree. Everywhere else, you're paying tax for nothing.

3️⃣ 𝗧𝗵𝗲 𝘀𝗲𝗻𝗶𝗼𝗿 𝗺𝗼𝘃𝗲 — Open React Profiler 𝘧𝘪𝘳𝘴𝘵. If it doesn't show wasted renders or a fat commit phase, you don't have a memoization problem — you have an unmeasured assumption. Memo is a fix, not decoration. Using it as decoration just adds noise to the dependency arrays you'll forget to update three weeks later.

The same logic holds for useCallback. Stable identity matters when something downstream actually needs it. Otherwise it's a wrapper around an allocation you were about to make anyway.

Most "optimized" code I review wasn't slow before the optimization. It was just unreadable after.

When do you reach for useMemo by default vs by measurement?
