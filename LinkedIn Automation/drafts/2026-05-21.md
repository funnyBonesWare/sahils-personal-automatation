𝗬𝗼𝘂𝗿 𝗱𝗮𝘀𝗵𝗯𝗼𝗮𝗿𝗱 𝗴𝗲𝘁𝘀 𝘀𝗹𝗼𝘄𝗲𝗿 𝗮𝗳𝘁𝗲𝗿 𝟰 𝗵𝗼𝘂𝗿𝘀. 𝗖𝗵𝗮𝗿𝘁.𝗷𝘀 𝗺𝗶𝗴𝗵𝘁 𝗯𝗲 𝘁𝗵𝗲 𝗿𝗲𝗮𝘀𝗼𝗻 — 𝗻𝗼𝘁 𝗥𝗲𝗮𝗰𝘁.

We had an operator tablet that felt fine at 9am and unusable by lunch. No new deploy. No spike in API traffic. Just the same three routes, opened and closed all morning.

Profiler showed heap growth tied to canvas nodes, not component count.

1️⃣ 𝗪𝗵𝗮𝘁 𝗖𝗵𝗮𝗿𝘁.𝗷𝘀 𝗹𝗲𝗮𝘃𝗲𝘀 𝗯𝗲𝗵𝗶𝗻𝗱 — Every chart instance registers plugins, animation frames, and resize observers. If you only unmount the React wrapper and never call chart.destroy(), the canvas and its internal state stay alive. Navigate away ten times in a shift and you've got ten ghost charts still listening for resize events.

2️⃣ 𝗪𝗵𝘆 𝗶𝘁 𝗵𝗶𝗱𝗲𝘀 — On localhost you open a page twice and call it done. In production, operators live inside one SPA for hours. They jump between fleet overview, session detail, and alerts — each route mounts a fresh Chart.js instance. Memory climbs slowly enough that nobody blames the chart until the whole tab stutters.

3️⃣ 𝗧𝗵𝗲 𝗳𝗶𝘅 𝗶𝘀 𝗯𝗼𝗿𝗶𝗻𝗴 𝗮𝗻𝗱 𝗲𝗮𝘀𝘆 𝘁𝗼 𝘀𝗸𝗶𝗽 — Hold the instance in a ref, call destroy() in useEffect cleanup, and don't recreate the chart on every parent re-render if only the data changed — update with chart.data.datasets[0].data = next and chart.update('none'). We wrapped that in a small hook so reviewers see cleanup in one place. After that, eight-hour sessions stopped eating RAM.

The senior habit isn't "switch to a lighter chart library." It's treating third-party instances like WebSocket connections: 𝘪𝘧 𝘺𝘰𝘶 𝘰𝘱𝘦𝘯𝘦𝘥 𝘪𝘵, 𝘺𝘰𝘶 𝘤𝘭𝘰𝘴𝘦 𝘪𝘵.

Do you destroy Chart.js (or similar) on unmount, or have you hit the slow-tab leak too?
