𝗢𝗽𝘁𝗶𝗺𝗶𝘀𝘁𝗶𝗰 𝗨𝗜 𝗹𝗼𝗼𝗸𝘀 𝗺𝗮𝗴𝗶𝗰𝗮𝗹 𝗼𝗻 𝗹𝗼𝗰𝗮𝗹𝗵𝗼𝘀𝘁. 𝗧𝗵𝗲 𝗳𝗶𝗿𝘀𝘁 𝘁𝗶𝗺𝗲 𝘁𝗵𝗲 𝘀𝗲𝗿𝘃𝗲𝗿 𝘀𝗮𝘆𝘀 𝗻𝗼, 𝗶𝘁 𝘁𝘂𝗿𝗻𝘀 𝗶𝗻𝘁𝗼 𝗮 𝗹𝗶𝗲.

Three years back I was building a side dashboard on my laptop — fake fleet, mocked WebSocket feed — to learn real-time UI patterns. I wired an optimistic toggle on a "start" button and called it done.

Then I flipped two switches in my mock layer: 300ms of latency, 30% random rejections.

The same row started flipping green → red → green on its own. No bug in my code. Just optimism without rollback.

1️⃣ 𝗢𝗽𝘁𝗶𝗺𝗶𝘀𝘁𝗶𝗰 𝗨𝗜 𝗶𝘀 𝗮 𝗯𝗲𝘁
You paint the change immediately and hope the server agrees later.

Cheap bet: a like count, a draft save, a list reorder. If you're wrong, no one cares.
Expensive bet: money moved, an email triggered, an inventory decrement. If you're wrong, the user already believed you.

2️⃣ 𝗧𝗵𝗲 𝘁𝗵𝗿𝗲𝗲 𝘄𝗮𝘆𝘀 𝗶𝘁 𝗯𝗿𝗲𝗮𝗸𝘀
Tutorials show the happy path. The real world has three messy ones.

The server rejects with a 4xx — your UI has to walk the change back.
The request times out — was it applied or not? You honestly don't know.
A stale WebSocket push lands mid-rollback — and overwrites your correction with old data.

Each one becomes a lie on screen if you don't plan for it.

3️⃣ 𝗙𝗼𝘂𝗿 𝗵𝗮𝗯𝗶𝘁𝘀 𝘁𝗵𝗮𝘁 𝗳𝗶𝘅 𝗶𝘁
𝗧𝗮𝗴 𝗽𝗲𝗻𝗱𝗶𝗻𝗴 𝗰𝗵𝗮𝗻𝗴𝗲𝘀 — give each one a client-side id and a pending flag the row can read.
𝗥𝗼𝗹𝗹 𝗯𝗮𝗰𝗸 𝘃𝗶𝘀𝗶𝗯𝗹𝘆 — animate back and show a short reason. Never snap silently.
𝗧𝗿𝘂𝘀𝘁 𝘁𝗵𝗲 𝘀𝗲𝗿𝘃𝗲𝗿 — if a WebSocket event arrives mid-flight, the server value wins.
𝗖𝗮𝗽 𝗽𝗲𝗻𝗱𝗶𝗻𝗴 𝘁𝗶𝗺𝗲 — a row stuck pending for 8 seconds should surface to the user, not stay as a spinner you forgot.

The lesson that day wasn't "optimistic UI is bad". It was 𝘥𝘰𝘯'𝘵 𝘱𝘢𝘪𝘯𝘵 𝘢 𝘧𝘶𝘵𝘶𝘳𝘦 𝘺𝘰𝘶 𝘤𝘢𝘯'𝘵 𝘩𝘰𝘯𝘰𝘂𝘳.

If the action is cheap to undo, be optimistic. If it's expensive or irreversible, show a spinner and tell the truth.

Where do you draw that line — optimistic by default, or only when the action is cheap to undo?
