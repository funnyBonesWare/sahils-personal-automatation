𝗡𝗼𝘁 𝗲𝘃𝗲𝗿𝘆 "𝗹𝗶𝘃𝗲" 𝗱𝗮𝘀𝗵𝗯𝗼𝗮𝗿𝗱 𝗻𝗲𝗲𝗱𝘀 𝗮 𝗪𝗲𝗯𝗦𝗼𝗰𝗸𝗲𝘁. 𝗜 𝗹𝗲𝗮𝗿𝗻𝗲𝗱 𝘁𝗵𝗮𝘁 𝘁𝗵𝗲 𝗲𝘅𝗽𝗲𝗻𝘀𝗶𝘃𝗲 𝘄𝗮𝘆.

Early in my frontend career, "real-time" meant WebSockets. Status page? Socket. Alert count? Socket. A config panel that changed twice a day? Somehow also a socket.

It felt senior. It was mostly 𝘮𝘢𝘪𝘯𝘵𝘦𝘯𝘢𝘯𝘤𝘦 I didn't budget for.

Now I run a short checklist before anyone on the team opens a socket connection.

1️⃣ 𝗣𝗼𝗹𝗹𝗶𝗻𝗴 + 𝗘𝗧𝗮𝗴 — If updates are every 30–60 seconds and users don't need sub-second latency, polling wins. Add ETag or If-None-Match — most polls return 304 and cost almost nothing. You get retries, caching, and standard load-balancer behavior for free. Boring. Correct for half the "live" UIs I've seen pitched as socket problems.

2️⃣ 𝗦𝗦𝗘 (𝗦𝗲𝗿𝘃𝗲𝗿-𝗦𝗲𝗻𝘁 𝗘𝘃𝗲𝗻𝘁𝘀) — Server pushes, client only listens. Great for alert streams, job progress, notification feeds. One direction, HTTP-friendly, auto-reconnect built into the browser API. You still need a resync story after disconnect — but you're not maintaining heartbeat logic for a dashboard that only needs server → client.

3️⃣ 𝗪𝗲𝗯𝗦𝗼𝗰𝗸𝗲𝘁𝘀 — I reach here when the product actually needs bidirectional, high-frequency updates: live cursors, collaborative edits, sub-second state users act on immediately. That's when the five-line API becomes five hundred lines — reconnect, backoff, sequence IDs, proxy timeouts, staging on spotty 4G.

The senior question isn't "can we use WebSockets?" It's "what happens when the connection lies?" Polling degrades to stale data with a timestamp. SSE degrades to reconnect + refetch. Sockets degrade to ghost UI state unless you planned for it.

I still love real-time UIs. I just stopped treating the socket as the default hammer.

Where do you draw the line — polling first, or sockets from day one?
