𝗧𝗵𝗲 𝗯𝘂𝗴 𝘄𝗮𝘀𝗻’𝘁 “𝘀𝗲𝗮𝗿𝗰𝗵 𝗶𝘀 𝘀𝗹𝗼𝘄”. 𝗜𝘁 𝘄𝗮𝘀 “𝘀𝗲𝗮𝗿𝗰𝗵 𝗶𝘀 𝗹𝘆𝗶𝗻𝗴”.

Picture a filter bar that calls an API on every change. Type “rea”, then quickly add “c”. The “rea” request returns after the “reac” request… and your UI snaps back to older results.

It looks like jank. It’s actually a correctness bug.

1️⃣ 𝗔𝗯𝗼𝗿𝘁 𝗼𝗹𝗱 𝗿𝗲𝗾𝘂𝗲𝘀𝘁𝘀 — Use AbortController so in-flight fetches get cancelled when input changes. You save server work, and you stop late responses from winning by accident.

2️⃣ 𝗔𝗱𝗱 𝗮 𝗿𝗲𝗾𝘂𝗲𝘀𝘁 𝗶𝗱 (𝗹𝗮𝘀𝘁-𝘄𝗿𝗶𝘁𝗲-𝘄𝗶𝗻𝘀) — Even with aborts, not every client / proxy / library behaves perfectly. Keep an incrementing request id; only commit results if the id matches the latest one you sent.

3️⃣ 𝗧𝗿𝗲𝗮𝘁 “𝘀𝗹𝗼𝘄” 𝗮𝗻𝗱 “𝘀𝘁𝗮𝗹𝗲” 𝗮𝘀 𝗱𝗶𝗳𝗳𝗲𝗿𝗲𝗻𝘁 — Debounce helps load. Abort + request ids help truth. If you only debounce, you can still render stale data… just less often.

The senior habit here is boring: assume responses can arrive out of order, because they will.

When you build type-ahead search, do you explicitly guard against stale responses, or rely on “it usually comes back in order”?
