𝗧𝘆𝗽𝗲𝗦𝗰𝗿𝗶𝗽𝘁 𝗰𝗮𝗻'𝘁 𝘀𝗮𝘃𝗲 𝘆𝗼𝘂 𝗳𝗿𝗼𝗺 𝗮 𝘁𝘆𝗽𝗲 𝘁𝗵𝗮𝘁 𝗹𝗶𝗲𝘀.

A few years back I shipped a fetch-and-render that worked beautifully on localhost — until production started returning { error: "rate-limited" } instead of { data: [...] }. The component cheerfully read .data, got undefined, and the panel went blank. No exception. No log line. Just nothing.

The bug wasn't the network. The bug was my type.

1️⃣ 𝗧𝗵𝗲 𝗳𝗮𝗸𝗲-𝗳𝗿𝗶𝗲𝗻𝗱𝗹𝘆 𝘀𝗵𝗮𝗽𝗲 — type ApiResponse<T> = { data?: T; error?: string }. It looks defensive. It isn't. TypeScript happily lets you read response.data when error is set, because optional means "maybe there". Two booleans of presence give you four possible states — only two of which are real. The compiler can't tell you which one you're in.

2️⃣ 𝗗𝗶𝘀𝗰𝗿𝗶𝗺𝗶𝗻𝗮𝘁𝗲𝗱 𝘂𝗻𝗶𝗼𝗻𝘀 𝗸𝗶𝗹𝗹 𝘁𝗵𝗲 𝗶𝗺𝗽𝗼𝘀𝘀𝗶𝗯𝗹𝗲 𝘀𝘁𝗮𝘁𝗲𝘀 — type ApiResponse<T> = { ok: true; data: T } | { ok: false; error: string }. Now the compiler refuses to let you touch data until you check ok. The "loading + data + error" tangle that lives in most hooks collapses into one tagged variant: { status: "idle" } | { status: "loading" } | { status: "success"; data } | { status: "error"; error }. No more rendering a spinner over stale data because three booleans drifted apart.

3️⃣ 𝗧𝗵𝗲 𝗽𝗮𝘁𝘁𝗲𝗿𝗻 𝗶𝘀 𝗯𝗶𝗴𝗴𝗲𝗿 𝘁𝗵𝗮𝗻 𝗳𝗲𝘁𝗰𝗵 — A multi-step form is a union, not a bag of optional fields. A WebSocket message is a union, not one object with "maybe a payload, maybe an error code". A reducer state is usually a union too. Anywhere 𝘵𝘸𝘰 𝘴𝘩𝘢𝘱𝘦𝘴 𝘤𝘢𝘯'𝘵 𝘣𝘰𝘵𝘩 𝘣𝘦 𝘵𝘳𝘶𝘦, optional fields are the wrong tool — even when the code typechecks.

The senior habit isn't fancier generics. It's making impossible states unrepresentable, then trusting the compiler to enforce it.

Where have discriminated unions saved you — and where do you still see "optional everything" shapes in your codebase?
