𝗬𝗼𝘂𝗿 𝗘𝗿𝗿𝗼𝗿 𝗕𝗼𝘂𝗻𝗱𝗮𝗿𝘆 𝘄𝗼𝗻'𝘁 𝗰𝗮𝘁𝗰𝗵 𝘁𝗵𝗲 𝗯𝘂𝗴 𝘆𝗼𝘂𝗿 𝘂𝘀𝗲𝗿 𝗷𝘂𝘀𝘁 𝗵𝗶𝘁.

Early in my frontend career I wrapped the whole app in one boundary and called it resilient. Then a chart plugin threw inside a click handler — the page didn't white-screen, but the click did nothing and there was no fallback UI. Users thought the button was broken. The boundary never fired.

I'd confused "React won't crash" with "the product is safe."

1️⃣ 𝗪𝗵𝗮𝘁 𝗯𝗼𝘂𝗻𝗱𝗮𝗿𝗶𝗲𝘀 𝗮𝗰𝘁𝘂𝗮𝗹𝗹𝘆 𝗰𝗮𝘁𝗰𝗵 — Render-phase errors in the tree below them: a bad valueGetter blowing up a cell renderer, a map over undefined in JSX, a third-party component throwing during paint. That's it. They show a fallback instead of unmounting the whole root. For a dashboard with five independent panels, that's worth gold — one bad widget shouldn't take down the nav, filters, and the rest of the grid.

2️⃣ 𝗪𝗵𝗮𝘁 𝘁𝗵𝗲𝘆 𝗱𝗼𝗻'𝘁 — Event handlers (onClick, onSubmit). Async code (fetch, setTimeout, WebSocket callbacks). Errors in the boundary's own render. Server Components errors on the server. I've seen teams add a boundary and still get silent failures because the throw happened in a .then() three frames later. For those you still need try/catch, error state in the hook, and something visible in the UI — not a class component at the root hoping for the best.

3️⃣ 𝗪𝗵𝗲𝗿𝗲 𝘁𝗼 𝗽𝗹𝗮𝗰𝗲 𝘁𝗵𝗲𝗺 — One app-wide boundary is a last resort, not a strategy. I now aim for route-level + widget-level: the alerts chart can fail while the session table keeps working. Pair each boundary with a small reset — "Try again" that clears local error state or remounts the widget key — so users aren't stuck on a dead panel until they refresh the tab.

Error boundaries are insurance for the render tree, not a substitute for handling async and interaction failures where they happen.

Do you use one global boundary, or isolate failures per route / widget?
