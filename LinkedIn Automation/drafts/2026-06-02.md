𝗢𝗻𝗲 𝗖𝗼𝗻𝘁𝗲𝘅𝘁 𝗮𝘁 𝘁𝗵𝗲 𝘁𝗼𝗽 𝗰𝗮𝗻 𝗿𝗲-𝗿𝗲𝗻𝗱𝗲𝗿 𝗲𝘃𝗲𝗿𝘆 𝘄𝗶𝗱𝗴𝗲𝘁 𝗼𝗻 𝗲𝘃𝗲𝗿𝘆 𝘀𝗼𝗰𝗸𝗲𝘁 𝘁𝗶𝗰𝗸.

A few years back I shipped a dashboard where theme, user prefs, filter state, and a live metrics blob all lived in one React Context. Profiler looked fine on localhost. In staging, a WebSocket pushed row counts every second — and the whole page reconciled: nav, filters, three charts, and a virtualized table that didn't even read the metric.

The bug wasn't the socket. It was that every consumer subscribed to the same value object.

1️⃣ 𝗪𝗵𝘆 𝗼𝗻𝗲 𝗺𝗲𝗴𝗮-𝗽𝗿𝗼𝘃𝗶𝗱𝗲𝗿 𝗵𝘂𝗿𝘁𝘀 — Context re-renders every component that calls useContext when the provider's value identity changes. Put fast-moving data next to slow-moving data in one { theme, filters, liveStats } object and you recreate the object every tick — so components that only care about theme still repaint. On a data-heavy UI that's how you get "React is slow" when the real issue is broadcast updates.

2️⃣ 𝗦𝗽𝗹𝗶𝘁 𝗯𝘆 𝘂𝗽𝗱𝗮𝘁𝗲 𝗳𝗿𝗲𝗾𝘂𝗲𝗻𝗰𝘆 — I now separate providers on purpose: UI chrome (theme, layout) almost never changes; filter/query state changes on user input; live streams get their own narrow context or a store with selectors. A chart panel that only needs alert count shouldn't sit under the same provider as a table listening to 800 row patches. Colocate state in the widget when nothing else needs it — global is a last resort, not a default.

3️⃣ 𝗪𝗵𝗲𝗻 𝗖𝗼𝗻𝘁𝗲𝘅𝘁 𝗶𝘀𝗻'𝘁 𝗲𝗻𝗼𝘂𝗴𝗵 — If many siblings need the same live slice, Context still works — but stabilize what you pass (memoized value objects, split contexts, or a small store with selectors so components subscribe to one field). The senior habit: before adding another field to AppContext, ask who re-renders when this field changes. If the answer is "everyone," you've found the next perf ticket.

Context is great for avoiding prop drilling. It's terrible as a single bucket for everything that moves at different speeds.

Do you split providers by update rate, or reach for a store with selectors first on dashboard apps?
