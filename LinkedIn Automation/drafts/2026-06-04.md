𝗬𝗼𝘂𝗿 𝗱𝗮𝘀𝗵𝗯𝗼𝗮𝗿𝗱 𝗱𝗼𝗲𝘀𝗻'𝘁 𝗻𝗲𝗲𝗱 𝘁𝗼 𝗿𝗲𝗻𝗱𝗲𝗿 𝘄𝗵𝗲𝗻 𝗻𝗼𝗯𝗼𝗱𝘆 𝗶𝘀 𝗹𝗼𝗼𝗸𝗶𝗻𝗴.

I used to leave WebSocket listeners and five-second polling hooks running 24/7 because "the data should stay fresh." Then I left a staging tab open overnight, came back to a laptop fan spinning, and React DevTools showed thousands of commits while the tab was buried behind Slack. The socket was fine. The tab wasn't the active surface — but the UI kept paying full price anyway.

Hidden tabs are a production environment most frontend perf guides skip.

1️⃣ 𝗪𝗵𝗮𝘁 𝘁𝗵𝗲 𝗣𝗮𝗴𝗲 𝗩𝗶𝘀𝗶𝗯𝗶𝗹𝗶𝘁𝘆 𝗔𝗣𝗜 𝗴𝗶𝘃𝗲𝘀 𝘆𝗼𝘂 — document.visibilityState flips to hidden when the user switches tabs, minimizes the window, or locks the screen. visibilitychange fires on that transition. It's not "user left the site forever" — it's "this document isn't the thing they're staring at right now." That's the right signal to pause expensive work, not tear down the whole session.

2️⃣ 𝗣𝗮𝘂𝘀𝗲 𝘂𝗽𝗱𝗮𝘁𝗲𝘀, 𝗱𝗼𝗻'𝘁 𝗱𝗿𝗼𝗽 𝘀𝘁𝗮𝘁𝗲 — On hidden: close or pause the WebSocket, clear refetchInterval on TanStack Query, stop requestAnimationFrame loops tied to live charts. On visible again: reconnect, refetch once, reconcile row data. I keep the last good snapshot on screen so the user doesn't see a blank grid flash — they see slightly stale data for two seconds, then a catch-up burst. That's cheaper than reconciling 40 chart points per tick into an invisible tab.

3️⃣ 𝗗𝗼𝗻'𝘁 𝗽𝗮𝘂𝘀𝗲 𝘄𝗵𝗮𝘁 𝘀𝗵𝗼𝘂𝗹𝗱 𝘀𝘁𝗮𝘆 𝗮𝗹𝗶𝘃𝗲 — Auth token refresh, error toasts for a failed mutation the user just triggered, and analytics you actually need can keep running. The filter is: does this update paint pixels or only warm the JS heap? If it's the latter and visibility is hidden, defer it. Pair with Page Lifecycle where you need mobile Safari quirks — but visibility alone fixes most desktop "I had twelve dashboard tabs open" stories.

Battery, fan noise, and "React feels heavy" on admin UIs often start with work that never reaches the screen.

Do you pause sockets and polling on hidden tabs, or let them run until the user closes the window?
