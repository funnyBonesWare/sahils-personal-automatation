𝗬𝗼𝘂𝗿 𝗪𝗲𝗯𝗦𝗼𝗰𝗸𝗲𝘁 𝗵𝗮𝗻𝗱𝗹𝗲𝗿 𝗶𝘀𝗻'𝘁 𝘀𝗹𝗼𝘄. 𝗖𝗮𝗹𝗹𝗶𝗻𝗴 𝘀𝗲𝘁𝗦𝘁𝗮𝘁𝗲 𝗼𝗻 𝗲𝘃𝗲𝗿𝘆 𝗺𝗲𝘀𝘀𝗮𝗴𝗲 𝗶𝘀.

A few years back I shipped a live status board where the socket pushed row patches 10–20 times per second. Profiling looked fine on the handler — sub-millisecond JSON parse. React DevTools told a different story: hundreds of commits per minute, charts jittering, and a virtualized grid that couldn't keep up because every message triggered a full reconcile.

The pipe was healthy. I was feeding React one grain of sand at a time.

1️⃣ 𝗪𝗵𝘆 𝗽𝗲𝗿-𝗺𝗲𝘀𝘀𝗮𝗴𝗲 𝘀𝗲𝘁𝗦𝘁𝗮𝘁𝗲 𝗵𝘂𝗿𝘁𝘀 — Each setState schedules a render. On a dashboard with multiple consumers, that's not "one cheap update" — it's a coordination burst. High-frequency streams (telemetry, price ticks, alert counters) don't need pixel-perfect freshness at 60fps; they need correct 𝘭𝘢𝘴𝘵 state at human-readable cadence. Batching turns 20 renders into one reconcile with 20 merged patches.

2️⃣ 𝗛𝗼𝘄 𝗜 𝗯𝗮𝘁𝗰𝗵 𝗻𝗼𝘄 — Buffer incoming messages in a ref. Flush on requestAnimationFrame (or a 50–100ms interval if the tab doesn't need 60fps). Merge patches into one object or map update before calling setState once. For out-of-order or duplicate messages, attach a sequence ID or timestamp and drop stale arrivals — ghost updates are worse than slightly delayed ones. On React 18+, wrapping that single setState in startTransition can also deprioritize the reconcile without losing the final snapshot.

3️⃣ 𝗗𝗼𝗻'𝘁 𝗯𝗮𝘁𝗰𝗵 𝘄𝗵𝗮𝘁 𝘁𝗵𝗲 𝘂𝘀𝗲𝗿 𝗷𝘂𝘀𝘁 𝗰𝗹𝗶𝗰𝗸𝗲𝗱 — User-initiated mutations (toggle, submit, drag) should stay immediate. The filter is: is this stream 𝘣𝘢𝘤𝘬𝘨𝘳𝘰𝘂𝘯𝘥 noise or 𝘥𝘪𝘳𝘦𝘤𝘵 feedback? Batch the noise. Never batch the button someone is staring at.

Production dashboards feel "heavy" long before the socket API is the bottleneck. Often it's React doing honest work too often.

Do you batch socket updates before they hit state, or let every message trigger its own render?
