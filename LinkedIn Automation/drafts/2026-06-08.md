Early in my frontend career I thought "just spread the API response into state" was clean code. Then I profiled a live table where each socket patch rebuilt row objects with keys in different order — React reconciled fine, but scroll jank showed up anyway. The grid wasn't struggling with 𝘥𝘢𝘵𝘢 volume. It was fighting object 𝘴𝘩𝘢𝘱𝘦 churn.

1️⃣ 𝗪𝗵𝗮𝘁 𝗩𝟴 𝗰𝗮𝗿𝗲𝘀 𝗮𝗯𝗼𝘂𝘁 — JavaScript engines optimize objects with stable hidden classes — consistent key order and types. Recreate { id, status, ts, value } every tick but shuffle key order or add ephemeral fields and the engine treats each row like a new shape. Row components doing shallow compares, memo, or dependency checks burn extra work. Same JSON payload, different perf story.

2️⃣ 𝗧𝗵𝗲 𝗯𝗼𝗿𝗶𝗻𝗴 𝗳𝗶𝘅 — Normalize incoming patches into stable templates. Fixed key order. Same fields on every row — use null instead of omitting keys. Keep row identity stable when nothing changed. In valueGetter paths, return primitives or cached objects, not inline { ...row, computed } every call. AG Grid's immutable data mode helps if you wire getRowId and don't rebuild the whole row map per tick.

3️⃣ 𝗪𝗵𝗲𝗻 𝗻𝗼𝘁 𝘁𝗼 𝗼𝗯𝘀𝗲𝘀𝘀 — If you've got 40 rows and one chart, ship it. This matters when virtualized grids, memoized row renderers, and high-frequency updates collide. Profile first — React Profiler plus the Performance tab — then fix shapes before reaching for Web Workers.

Perf bugs on data-heavy UIs often look like "the library is slow" when it's unstable object graphs under the hood.

Do you normalize row shapes before they hit grid state, or merge API patches as-is?
