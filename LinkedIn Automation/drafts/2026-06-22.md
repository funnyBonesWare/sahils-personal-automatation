𝗧𝗵𝗲 𝗩𝗲𝗿𝗰𝗲𝗹 𝗔𝗜 𝗦𝗗𝗞 𝗱𝗲𝗺𝗼 𝗶𝘀 𝗼𝗻𝗲 𝗳𝗶𝗹𝗲. 𝗣𝗿𝗼𝗱𝘂𝗰𝘁𝗶𝗼𝗻 𝗶𝘀 𝘁𝗵𝗿𝗲𝗲 𝗹𝗮𝘆𝗲𝗿𝘀.

I shipped a chat sidebar on a side Next.js app with useChat and a /api/chat route. Tokens streamed. Looked great in the demo. Then I added tool calls, message history, and a model swap. Things broke in quiet ways. Wrong context sent to the model. Tool results rendering twice. API costs spiking because nothing gated the route.

The SDK is not one hook. It is a split architecture. Understanding that split is the difference between a tutorial and something you can ship.

1️⃣ 𝗖𝗹𝗶𝗲𝗻𝘁: 𝗨𝗜𝗠𝗲𝘀𝘀𝗮𝗴𝗲 𝗮𝗻𝗱 𝘀𝘁𝗿𝗲𝗮𝗺𝗶𝗻𝗴 𝗽𝗮𝗿𝘁𝘀

useChat from @ai-sdk/react owns what the user sees. Messages carry UI metadata: timestamps, tool invocation cards, partial text chunks as they arrive. In SDK 5 this runs through a transport (DefaultChatTransport pointing at your route). The client does not call OpenAI directly. It consumes an SSE data stream and maps parts to React. Your job on the frontend is rendering parts, not reimplementing the protocol.

2️⃣ 𝗦𝗲𝗿𝘃𝗲𝗿: 𝘀𝘁𝗿𝗲𝗮𝗺𝗧𝗲𝘅𝘁 𝗮𝗻𝗱 𝘁𝗵𝗲 𝗺𝗼𝗱𝗲𝗹 𝗯𝗼𝘂𝗻𝗱𝗮𝗿𝘆

The route handler is where the API key lives. streamText picks the model, runs tools, and streams back through toUIMessageStreamResponse(). Before the model runs, you convert UIMessage[] to ModelMessage[] with convertToModelMessages(). That strips UI-only fields the model should never see. Skip that step and you ship bloated context, leaked metadata, or a history shape the provider rejects. Server owns auth, rate limits, and which tools exist. Client owns display.

3️⃣ 𝗪𝗵𝗮𝘁 𝘀𝘁𝗶𝗹𝗹 𝗯𝗿𝗲𝗮𝗸𝘀 𝗮𝗳𝘁𝗲𝗿 𝘁𝗵𝗲 𝗱𝗲𝗺𝗼

Treating the hook as the whole stack. Putting keys in the browser to "move faster." Assuming streaming is just appending text when tools and reasoning need part-level UI. Upgrading from SDK 4 to 5 without reading the transport and message type changes. AI can paste the starter route in minutes. It will not wire your trust boundary, tool allowlist, or cost guardrails.

The chat bubble is the easy layer. The route handler contract is the product.
