I wired a task board on a side Next.js app with useOptimistic and a Server Action. Toggle status, list updates instantly, feels great. Then I throttled the network, double-clicked save, and opened two tabs. Three duplicate tasks with the same title. UI rolled back on failure once. It did not dedupe two in-flight POSTs. React Strict Mode in dev made it worse.

The hook solved rendering. It did not solve distributed mutation.

1️⃣ 𝘂𝘀𝗲𝗢𝗽𝘁𝗶𝗺𝗶𝘀𝘁𝗶𝗰 𝗶𝘀 𝗽𝗿𝗼𝗷𝗲𝗰𝘁𝗶𝗼𝗻, 𝗻𝗼𝘁 𝘁𝗿𝘂𝘁𝗵

useOptimistic patches local state inside a transition. Fail the action, React reverts. That is real and useful. But overlapping async actions can entangle rollback timing (there are open React issues on this). Treat optimistic state as temporary UI. Canonical data still lives on the server response. Never ship financial or inventory state on optimistic alone.

2️⃣ 𝗖𝗹𝗶𝗲𝗻𝘁 𝗹𝗮𝘆𝗲𝗿: 𝗶𝗻𝘁𝗲𝗻𝘁 𝗜𝗗 + 𝗶𝗻-𝗳𝗹𝗶𝗴𝗵𝘁 𝗴𝘂𝗮𝗿𝗱

Generate one idempotency key per user intent, not per HTTP retry. Disable the button on isPending. Debounce alone will not save you on mobile double-tap. If the user retries after a timeout, send the same key so the API returns the existing row instead of creating a second one. I keep the key in a ref tied to the form submit, not regenerated on every render.

3️⃣ 𝗦𝗲𝗿𝘃𝗲𝗿 𝗹𝗮𝘆𝗲𝗿: 𝗱𝗲𝗱𝘂𝗽𝗲 + 𝘃𝗲𝗿𝘀𝗶𝗼𝗻 𝗴𝘂𝗮𝗿𝗱

Store idempotency keys with a short TTL. On match, return 200 with the original entity. Add a revision field or ETag. Stale write gets 409 plus the latest snapshot. Client rebases UI from that payload instead of guessing. TanStack Query or SWR help reconcile cache after conflict. useOptimistic alone cannot.

The senior stack is four layers: optimistic render, client intent tracking, server dedupe, conflict merge. Skip any one and the demo still looks finished.
